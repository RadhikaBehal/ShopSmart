# Implementation plan and progress

## Product delivery sequence

1. **Workspace and product foundation** — inspect the workspace, define architecture and a build sequence. **Done:** greenfield Vite/React/TypeScript foundation; architecture decision record and this checklist.
2. **Customer storefront MVP** — make catalog discovery, category filtering, sorting, wishlisting, and bag interactions usable at desktop and mobile sizes. **Complete:** product lists, category counts, search (including specifications), category/seller/price/availability filters, rating/price/newest sorting, pagination, product details, ordered multi-image gallery, variants, stock, price, currency, seller and review summaries are served by the API. `ProductImage` and `ProductSpecification` are related records; the additive migration backfills prior image URL/alt text before removing legacy columns. Product images have an accessible fallback. API failures show retry states, never fabricated product cards. The bag/wishlist remain browser-persisted demonstrative features and checkout remains disabled. **Verified:** API-client, gallery and product-rendering tests, frontend lint/build, API build/unit and database integration tests, applied migrations, and live browser-to-API-to-PostgreSQL checks.
3. **Commerce API and identity** — modular Express API, validation, OpenAPI, PostgreSQL/Prisma, secure authentication, RBAC, rate limiting, and audit events. **Identity implementation complete:** salted scrypt passwords; ten-minute JWT access tokens bound to a database refresh session; rotating, hashed, 30-day httpOnly refresh cookies; logout/password-reset session revocation; current-database role checks; customer, seller, seller-staff, moderator, support-agent, admin and super-admin roles; customer self-registration; profile editing; ownership and admin-only API middleware; one-time email verification and password-reset tokens hashed at rest; origin protection; endpoint-specific rate limits; and audit entries for session/profile/security events. **Verified:** schema validation, additive identity migration, API build/unit tests, PostgreSQL-backed register/login/invalid credentials/profile/ownership/RBAC/verification/reset/refresh/expiry/logout integration tests, frontend auth-client tests, and live browser registration/session restoration/profile update/logout. Email delivery requires the configured external HTTP provider contract.
4. **Catalog and multi-vendor operations** — relational catalog/variants/inventory, seller onboarding, moderation, inventory reservations, and seller storefronts. **Seller ecosystem implemented:** customers can save/edit one application and submit it for review; administrators can filter and inspect applications, request information, approve/reject with notes, view history, and suspend/reactivate sellers. Approval and role activation are transactional; seller APIs check current database roles, approved application state, active seller status and authenticated ownership. Approved sellers can manage public store profiles and policies. **Phase 5B seller product APIs implemented:** approved active sellers can list/filter, create, retrieve, update and archive only their own products; new listings are DRAFT/PENDING_REVIEW and initial positive stock is recorded atomically in the inventory ledger. Edits to approved customer-facing content return it to review; seller edits preserve DISABLED moderation decisions. **Phase 5C seller inventory APIs implemented:** atomic stock adjustments use PostgreSQL row locks and commit the stock update with its immutable before/change/after ledger row; sellers can configure thresholds, list paginated history and detect their low-stock variants. **Phase 5D administrator product moderation APIs implemented:** ADMIN/SUPER_ADMIN users can query the pending queue, inspect products, approve pending products, disable pending/approved products with a reason, or explicitly return disabled products to pending review. Each transition conditionally updates moderation state and writes an audit event in one transaction. Public catalog list/detail/category queries expose only APPROVED products, with existing products grandfathered approved by the additive `20261102140300_product_moderation_inventory_ledger` migration. **Deferred:** seller/admin product/inventory UI, notifications, order fulfillment, seller payments/settlements, analytics, staff, document collection, and KYC.
5. **Checkout and order lifecycle** — transactional parent and seller orders, idempotency, Razorpay test integration and signed webhooks, refunds, returns, and notifications. **Not started.**
6. **AI service** — separate FastAPI deployment, intent extraction, semantic retrieval, recommendation and bundle baselines, review sentiment, explainability, and offline evaluation datasets/metrics. **Baseline implemented:** deterministic category/budget extraction, lexical catalog ranking, and explainable sentiment lexicon endpoints; **3 pytest tests pass**. These are not trained ML/semantic AI. Recommendations/bundles, data provenance, offline evaluation, and metrics are not implemented. The browser filter is also a local catalog heuristic, not semantic AI.
7. **Community and circular commerce** — verified-purchase reviews, product Q&A, resale/refurbishment, ownership, warranty, and repair discovery. **Not started.**
8. **Seller/admin surfaces** — seller application review and seller account management are implemented in Milestone 4. **Not started:** seller analytics and fulfillment, product moderation, dispute handling, settlement reports, and broader audit review.
9. **Quality and operations** — unit/integration/E2E tests, observability, caching/jobs, security review, performance, accessibility, and failure-state validation. **Partially verified:** focused frontend/API/Python tests, frontend build/lint, PostgreSQL auth/catalog integration, and responsive browser interactions. **Remaining:** full Playwright suite in CI, caching/jobs, load/accessibility/security audits, and deployment smoke tests.
10. **Deployment** — Docker Compose, GitHub Actions, environment validation, and Vercel/Render deployment guides. **Foundation implemented:** web/API/AI container recipes, Compose services, nginx SPA fallback, and CI jobs. The API container runs Prisma deploy migrations on startup. **Remaining:** provider-specific deployment smoke tests and email-delivery credentials/configuration.

## Current interaction contract

- Search terms, category slug, INR maximum budget, supported price sorting, and page selection are sent to the catalog API; category and budget intent extraction is deterministic, not remote AI inference.
- Product cards and details reflect the current published database records, including prices in minor units, active variants, inventory, ordered image galleries, specifications, seller/category, and available review summaries.
- A catalog API failure displays an actionable error and retry; it never falls back to local product fixtures.
- Wishlist and bag survive reloads in browser localStorage; this is demo-only persistence, not account-synced state.
- Checkout is visibly disabled and explains that no order/payment is processed; a success state is not fabricated.
- Seller draft, review, approval, role activation, profile, suspension, and public store state is stored in PostgreSQL. Application addresses are not returned by the public storefront API; only published seller products from the catalog API are displayed.
- Seller product/inventory APIs are available to approved active sellers; seller UI, automated notifications and fulfillment controls remain unimplemented.
- Circular commerce, help, and newsletter entry points disclose that those services are not connected.
